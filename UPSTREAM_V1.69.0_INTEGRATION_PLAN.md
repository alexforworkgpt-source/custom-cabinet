# План обновления Custom Cabinet: v1.66.0 → v1.69.1

Дата исследования: **2026-09-05**. Актуализация: **2026-09-06**.
Статус: **локальная интеграция реализована и проверена; runtime/Release-этапы не начаты**.

Рекомендация: сохранить завершённый перенос до Upstream Cabinet v1.69.0 и
добавить точный инкремент v1.69.1, сохранив наши интерфейс и сценарии. Для
полного комплекта v1.69.1 нужен отдельный runtime-gate с Upstream Bot v4.5.0;
v4.4.0 не содержит всех новых endpoint и payload. Промежуточные версии отдельно
на production устанавливать не нужно.
Работу выполнять последовательными тематическими этапами с проверками.

Разделы 1–8 сохраняют план и доказательства полного переноса v1.66.0–v1.69.0.
Точный инкремент v1.69.0–v1.69.1 и его фактический итог записаны в разделе 9,
чтобы не смешивать уже завершённые 96 commits с новыми 12 commits.

Полный вариант затрагивает **Custom Cabinet, сборщик Installer и Upstream Bot**.
Обновить только frontend и считать все новые функции совместимыми с Bot v4.1.0
нельзя: нужных API в проверенном исходном коде этой версии нет.

## 4. Последовательность реализации

### Шаг 1. Зафиксировать исходное состояние

**Где:** `custom-cabinet/`, отдельная рабочая копия и ветка обновления.
**Что:** начать от `96c34492fdbd1cc96feaab10d12494dd780d876d`; перед стартом
снова проверить HEAD и изменения. Если HEAD продвинулся, обновить трёхстороннее
сравнение. Сохранить отдельно существующие локальные работы. Выполнить исходные
проверки на неизменённом коде и записать известные browser failures.
**Почему:** новые ошибки нужно отличать от состояния до обновления.
**Готово:** записаны три точных SHA, исходные результаты и границы работ.

### Шаг 2. Закрыть серверный контракт

**Где:** отдельная исследовательская/тестовая копия Upstream Bot и документы
совместимости Custom Cabinet.
**Что:** проверить Bot v4.4.0 против v4.1.0: API из таблицы выше, права,
подарочные `gift_code`/`bot_claim_url`/`cabinet_claim_url`, env defaults,
платёжные callbacks, фоновые задания и миграции `0107`–`0114`.
Проверить старые записи пользователей, подписок, платежей и рефералов на
изолированных данных. Конфигурацию бизнеса сохранять: обновление не должно само
переключать схему рефералов, включать grace, платежные провайдеры или рассылки.
**Почему:** присутствие нового интерфейса не гарантирует правильной работы Bot.
**Готово:** матрица «запрос → ответ → право → тест», выбранная migration policy
и перечень проверок Bot. Неустановленная совместимость блокирует Release.

### Шаг 3. Подготовить сборку Custom Cabinet и Installer

**Где:** `custom-cabinet/package.json`, lockfile, Dockerfile, `.nvmrc`, CI,
конфигурации Vite/Vitest/TypeScript; отдельно `installer/scripts/release_bundle_publication.py`
и `installer/tests/test_release_bundle_publication.py`.
**Что:** согласованно перейти на проверенную Node.js `>=24.15.0`, разобрать
изменения React Router 7 → 8 и зависимостей из upstream. При исследовании была
обнаружена Node.js `24.11.1`, она ниже заявленного требования; итоговые
candidate-проверки выполнены на Node.js `24.19.0`. Сохранить наши
дополнительные пакеты, тесты, нейтральные metadata и закрепления версий.
Lockfile пересоздавать через npm только для осознанно выбранных изменений.

В Installer текущий сборщик ожидает ровно `FROM node:20-alpine AS builder`.
Dockerfile upstream содержит `FROM node:24-alpine AS builder`, поэтому прямой
перенос будет отклонён с `Cabinet Dockerfile base image contract changed`.
Добавить строго проверяемую поддержку нового варианта, сохранив старую;
не отключать проверки структуры и закрепления образов через digest.
Сначала тест на новый допустимый Dockerfile и отклонение неправильных вариантов,
потом минимальная правка. Выбрать точный Node builder digest для новой сборки.
**Почему:** обычная локальная сборка не проверяет публикацию через Installer.
**Готово:** новые и прежние формы Dockerfile проверяются, Release-сборка
воспроизводится; изменения двух проектов остаются в отдельных историях.

### Шаг 4. Перенести исправления запуска и надёжности

**Где:** `src/utils/`, `src/store/auth.ts`, `src/i18n.ts`, `src/main.tsx`,
`src/App.tsx`, `src/AppWithNavigator.tsx`, связанные hooks/providers Custom Cabinet.
**Что:** перенести безопасный доступ к localStorage/sessionStorage, включая
наши дополнительные вызовы; защиту от бесконечного reload; сохранение OAuth
state и сессии; исправление Object.hasOwn; ожидание переводов и темы.
Использовать `diagnose` и `tdd` для воспроизводимых ошибок: сначала управляемая
задержка/ошибка загрузки переводов, затем исправление и повторная проверка.
Отдельно проверить язык Telegram, отличающийся от языка браузера, и ограниченное
ожидание всех startup-обещаний, чтобы неисправная сеть не оставляла пустой экран.
**Почему:** этот слой влияет сразу на вход, Dashboard, навигацию и платежи.
**Готово:** нет исключений при запрещённом storage, циклов reload и зависания
старта; обычная отложенная загрузка локали не оставляет ключи вместо подписей.

### Шаг 5. Перенести новые функции тематическими блоками

**Где:** `src/api/`, `src/types/`, маршруты, соответствующие `src/pages/`
и feature-компоненты Custom Cabinet.
**Что:** сначала types/API, затем состояния и операции, затем представление.

| Очерёдность | Блок | Что проверяет приёмка |
| --- | --- | --- |
| 5.1 | Подарки и ссылка из тикета на пользователя | Canonical gift links открывают нужную активацию; короткий display token не подменяет claim code; права на профиль соблюдаются |
| 5.2 | Реферальные уровни, ранги, деньги/дни | Дни не показываются как «0 ₽»; режимы chain/tiers различаются; частичное сохранение не затирает параллельный выбор из Bot; `null` отличается от отсутствующего поля; env-блокировки и legacy import учитываются |
| 5.3 | Grace-доступ | Права чтения/изменения, поля env только для чтения, проверка squad UUID, ответы 422, состояния observe/true/drain/false, необходимость перезапуска |
| 5.4 | Системные ошибки | Фильтры/пагинация, детали и исход доставки; право `system_errors:read` и отдельное право повторной отправки; ошибки API не маскируются пустым списком |
| 5.5 | TabPay и ParityPay | Методы видимы только при разрешении backend; top-up, pending/success/failure/cancel, возврат и гостевые сценарии на sandbox; прежние провайдеры сохраняют поведение |
| 5.6 | Email-шаблоны и превью | Общая обёртка, обязательные placeholders, серверное превью, переключатель, `can_disable=false`, санитизация/изоляция HTML; отказ API не выдаётся за успешное сохранение |

**Почему:** тематические блоки позволяют проверить каждое поведение отдельно.
**Готово:** тесты проверяют результат действий и отказов; новые операции на
реальных платежах и production-рассылках для проверки не выполняются.

### Шаг 6. Сохранить наш интерфейс и встроить визуальные исправления

**Где:** `src/components/layout/AppShell/`, Dashboard, Subscription, Connection,
Support, Profile, `src/styles/globals.css`, primitives и четыре locale-файла.
**Что:** сохранить быстрый QR, инструкции и информационный раздел, ясное
управление подпиской, наши dialogs/sheets, навигацию, восстановление прокрутки,
оформление Dashboard и Profile. Встроить skeleton-состояния через существующие
компоненты; не создавать второй независимый набор стилей. Не удалять «мёртвые»
upstream-компоненты и типы, пока не проверены их вызовы в Custom Cabinet.

Отдельно адаптировать цвета оператора, title/favicon/ярлыки, первый кадр,
верхние/нижние отступы и вырезы экрана в iOS. Сохранить runtime branding из Bot
и единый нейтральный Release Bundle. Обновить `ru`, `en`, `fa`, `zh`, сохранив
используемые нами ключи и RTL. Лицензии и техническое происхождение сохраняются.
**Почему:** большая часть входящих файлов пересекается с нашим дизайном.
**Готово:** все состояния видимы в нашей дизайн-системе без потери доработок.

### Шаг 7. Пройти проверки Custom Cabinet

**Где:** отдельная рабочая копия Custom Cabinet и браузеры тестового стенда.
**Что:** выполнить `npm test`, `npm run type-check`, `npm run build`,
`npm run check`, `npm run test:e2e`. Для изменённых конфигураций сборки также
проверить их TypeScript-конфигурацию, если обычный build её больше не охватывает.

Browser-матрица: ширины 320/375/768/1024/1280+, web и Telegram; тёмная,
светлая и операторская темы; ru/en и RTL, проверка всех четырёх словарей;
клавиатура, фокус и доступные названия. Сценарии: login/OAuth/callbacks,
Dashboard и состояния подписок, QR/подключение/подарок, top-up и возврат,
профиль/поддержка/инструкции, новые формы админки и отказ в доступе.
Для iOS добавить Safari/standalone и реальный Telegram, включая альбомный режим.

**Где:** production VPS и отдельный актуальный runbook перехода.

а не к установленному точному Release Bundle от 5 сентября.
**Готово:** точные версии и checksum совпали, сервисы исправны и smoke прошёл.

## 5. Откат и условия остановки

1. **До production, на стенде:** подготовить восстановление состояния прямо
   перед обновлением — Cabinet artifact, Bot SHA, образы и согласованный dump.
   Git SHA прежнего frontend сам по себе не является готовым откатом.
2. **Во время Protected Update, на VPS:** при `rolled_back` Installer уже
   выполнил возврат; проверить исходные identity и сервисы. При `safely_stopped`
   следовать сохранённому recovery plan; ручной запуск Bot не заменяет восстановление.
3. **После `committed`, на VPS:** текущий Installer не предоставляет отдельный
   поздний rollback по прежней Bundle identity. До rollout нужен проверенный
   отдельный recovery-план, учитывающий новые записи после обновления. Возврат
   старого frontend или ручной downgrade схемы не считать достаточным решением.
4. **На любом этапе:** остановить Release при неизвестном API-контракте,
   непроверенной migration policy, потере наших сценариев, провале обязательных
   тестов, невоспроизводимой сборке или отсутствии восстановления. Недоступную
   проверку записывать как непроверенную; прошлое исключение для Release от
   5 сентября не является доказательством качества нового кода.

переводы, темы, мобильные отступы и доступность. Новые Bot-зависимые функции
оставить вне этой поставки с точным списком пропусков; сборку и зависимости
проверить отдельно. Не объявлять такой результат полной интеграцией v1.69.0.
**Почему:** это уменьшает объём первого перехода, но требует отдельной матрицы
совместимости. Основная рекомендация этого плана — полный согласованный комплект.
