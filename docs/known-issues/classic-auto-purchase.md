# Classic: автопокупка после пополнения заблокирована

Статус на 2026-09-30: **дефект открыт; новая classic-автопокупка не работает
на проверенном Upstream Bot**. Изменения Custom Cabinet ниже исправляют
интерфейс и маршрут обычного продления, но не серверное исполнение новой покупки.
Backend в рамках этой работы не изменялся.

## Проверенные версии и причина

| Компонент | Точная опорная версия |
| --- | --- |
| Upstream Bot | `v4.15.0` / `877690a7039d1326b2c00eda3e297879b80c0678` |
| Upstream Cabinet | `v1.79.0` / `821c7b71823573a756de00418acb25118ede1c9c` |
| Custom Cabinet до локального исправления UI | `1169e3cb964caec9a9500ace89bbb53b7e5a89df` |
| Release Bundle, в котором наблюдался дефект | `v2026.09.29` |

Новая classic-покупка идёт через `POST /cabinet/subscription/purchase`.
При недостаточном балансе сервер сохраняет `cart_mode=subscription_purchase`
и `return_to_cart=true`, затем отвечает HTTP402. `cart_mode` — тип сохранённой
операции, а intent — временная серверная метка намерения завершить её после
пополнения. Custom Cabinet не задаёт `cart_mode` в запросе.

После зачисления платежа Upstream Bot находит корзину, но
`_process_single_cart` не поддерживает `subscription_purchase`: пишет
предупреждение о неизвестном mode и возвращает `False`. Generic classic flow
обрабатывает только корзины **без** mode; неизвестный mode туда не попадает.
Баланс зачислен, покупка не завершена. Изменение надписи или маршрута пополнения
не устраняет эту несовместимость.

Точные источники в
[`Upstream Bot`](https://github.com/BEDOLAGA-DEV/remnawave-bedolaga-telegram-bot/tree/877690a7039d1326b2c00eda3e297879b80c0678):

- `app/cabinet/routes/subscription_modules/purchase.py`, `submit_purchase`,
  обработчик `PurchaseBalanceError` около строки 627 — producer корзины.
- `app/services/user_cart_service.py`, `save_user_cart` около строки 42 —
  сохранение корзины и top-up intent с TTL, то есть сроком действия.
- `app/services/payment/common.py` около строки 398 — обработка корзины после
  зачисления.
- `app/services/subscription_auto_purchase_service.py`, `_process_single_cart`
  около строки 3114 и `auto_purchase_saved_cart_after_topup` около строки 3487 —
  dispatcher и проверка intent.

Дополнительный подтверждённый дефект: `/purchase` и `/renew` игнорируют
`False` из `save_user_cart` и сообщают `cart_saved=true`. Запись intent также
может не состояться. HTTP402 с этим флагом сам по себе не доказывает, что Redis
сохранил все данные для будущего исполнения.

## Воспроизведение

Воспроизводить только в изолированной тестовой среде, с тестовыми
PostgreSQL/Redis, аккаунтом и sandbox-провайдером платежей. У работающего Bot
должна быть включена автопокупка после пополнения. Проверять эффективную настройку
процесса с переопределениями из БД: отдельный импорт config может показать default.

1. В Custom Cabinet открыть `/subscription/purchase` в `sales_mode=classic`.
   Выбрать период, трафик, серверы и устройства. Баланс должен быть меньше цены.
2. Нажать «Пополнить баланс». Проверить отправку выбранных параметров через
   `/cabinet/subscription/purchase`, ответ HTTP402 с `cart_saved=true` и
   `cart_mode=subscription_purchase`. На сервере проверить фактическую корзину
   и intent, не полагаясь только на ответ API.
3. Выполнить sandbox-пополнение до достаточного баланса до истечения TTL.
   Закрыть Custom Cabinet: исполнение должно работать на сервере без открытой
   страницы и без повторного нажатия.
4. Проверить журнал, баланс, транзакцию покупки, целевую подписку и доступ в
   Remnawave. На проверенной версии баланс пополняется, dispatcher пропускает
   `subscription_purchase`, а новая покупка не появляется.

Для воспроизведения ложного `cart_saved` в backend-тесте подменить результат
`save_user_cart` на `False`. `/purchase` всё равно возвращает `cart_saved=true`.
Не отключать Redis на production для такого теста.

Готовые локальные материалы исследования находятся в игнорируемой папке
`.scratch/classic-payment/`: `backend-fix-request-20260930.md`,
`REPRODUCTION.md` и `reproduce_classic_cart.py`. Они являются дополнительными
артефактами владельца и не требуются для приведённого сценария в чистом checkout.
Повторное расследование версий для этой задачи не требуется.

Source-backed скрипт исполняет извлечённые настоящие функции `/purchase` и
top-up dispatcher, подменяя внешние сервисы и блокируя незаявленные imports.
Наблюдаемый дефект и controls дают 6 PASS; `--require-fixed` даёт 4 PASS и
2 ожидаемых FAIL: пропущенная покупка и ложный результат сохранения.
6 PASS здесь означает «дефект воспроизведён», а не «автопокупка исправлена».
Mocks соответствуют exact Bot v4.15.0; для исправленной версии их необходимо
проверить и адаптировать либо перенести сценарии в штатные backend-тесты.

## Что исправлено и что остаётся ограничением

- У classic-покупки одна кнопка: «Пополнить баланс» при нехватке средств,
  «Оплатить» при достаточной сумме. Подсказка честно сообщает о необходимости
  вернуться к выбору и подтвердить покупку с баланса на текущем backend.
- Обычное продление платной classic-подписки из управления ведёт на
  `/subscriptions/:id/renew`. После выбора периода `/renew` сохраняет
  поддерживаемый `extend`; интерфейс сразу открывает выбор оплаты при HTTP402
  с сохранённым `extend` и положительной недостающей суммой. Продление
  использует текущие параметры, а не новую настройку через `/purchase`.
- Trial, daily, limited, legacy/migration и тарифные сценарии имеют отдельные
  правила; их нельзя массово перенаправлять на classic-renewal.
- Frontend блокирует повторный клик во время запроса, но не обеспечивает
  серверную защиту от параллельных callbacks и не исправляет ложный `cart_saved`.
- Для `extend` сохраняются ограничения исходного исследования: раздельные
  commits списания/продления с компенсацией, недоказанная защита от повторного
  списания, возможный `None` при panel sync и различия direct/auto reset правил.
- Изменённые цена, скидки, параметры, TTL и статус между выбором и исполнением
  требуют серверных проверок. Остаток на балансе не является подтверждением покупки.
- Локальные unit/browser-тесты подменяют API. Они не подтверждают реальные
  платежи, исполнение в Redis/PostgreSQL, Telegram или доставку в Remnawave.
- Автоматический повтор POST после `balance.topup` не добавлять: событие
  означает зачисление денег и может конкурировать с backend-исполнением.
- Откат старого UI сам по себе не исправляет несовместимый mode. Backend и
  production в этой работе не изменяются; этот документ не разрешает откат.

## Условия повторной проверки после исправления разработчиком

До начала записать новый точный tag/SHA Upstream Bot, ссылку на исправление,
Custom Cabinet source SHA и checksum проверяемого artifact, тестовые image
digests, backend contract/configuration schema, target OS и sandbox-среду.
Не считать изменяемый `main` доказательством совместимости.

1. На новой версии проверить связь producer → dispatcher для
   `subscription_purchase`, фактическое сохранение корзины и intent, честный
   `cart_saved` при `False`/ошибке Redis и положительную `missing_amount`.
   Исходные два failing-сценария должны стать PASS, сохранив проверки контроля.
2. Проверить новую покупку с нулевым/частичным балансом и закрытым Cabinet:
   одно зачисление, одна покупка, одно списание, выбранные период/трафик/серверы/
   устройства и фактический доступ в панели без нового действия пользователя.
3. Проверить trial → paid и существующую целевую подписку: ID принадлежит
   пользователю, другая подписка не изменяется. Для active/expired renewal
   проверить срок, устройства, серверы, пакеты трафика и reset-настройки.
4. С настоящими тестовыми PostgreSQL/Redis проверить повторные и параллельные
   callbacks, конкуренцию с ручным запросом и перезапуск между этапами:
   ровно одна финансовая операция. Последовательных mocks для этой гарантии мало.
5. Проверить частичное пополнение, отсутствие/истечение intent и TTL, чужой ID,
   ограничения пользователя, недоступные параметры, смену sales mode,
   изменённую цену/скидку и ошибку панели. Нет лишнего списания или ложного успеха;
   цена соответствует согласованным условиям, повтор доставки не повторяет покупку.
6. Выполнить Custom Cabinet unit/type/build/browser gate, затем staging web
   и Telegram-проверки по [LIVE_CHECK.md](../../LIVE_CHECK.md). Подтверждать
   покупку состоянием операции/подписки, а не одним `balance.topup`.
7. При новом Bot SHA повторить применимый full Installer lifecycle: старый proof
   нельзя автоматически переносить на изменившуюся связку. Точные новые версии
   включить в новый immutable Release Bundle после всех необходимых проверок.

После успешных проверок сохранить результаты, версии и логи без секретов и
персональных данных. Только тогда пересмотреть ручную classic-подсказку,
описание релиза и статус этого дефекта. Публикация и production-проверка требуют
отдельного разрешения владельца.

## Решение для Release Bundle

С текущим Upstream Bot новая classic-автопокупка остаётся известным дефектом.
По [LIVE_CHECK.md](../../LIVE_CHECK.md#release-blocking-conditions) неработающая
покупка является release blocker. Подготовка diff, локальных проверок и описания
релиза допустима; документирование дефекта не превращает общий gate в PASS.
На 2026-09-30 владелец явно разрешил выпуск Custom Cabinet в Release Bundle
`v2026.09.30` с ручным подтверждением новой classic-покупки после пополнения,
приняв это известное ограничение как исключение для данного релиза. Это решение
не закрывает дефект и не отменяет остальные применимые проверки. Backend и
production этим решением не изменяются. UI и маршрут продления описывать как исправленные;
новую автопокупку и настоящее серверное автопродление — как не подтверждённые.
