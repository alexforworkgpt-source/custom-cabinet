# Скидочные баннеры Custom Cabinet — аудит 2026-10-20

Статус: **аудит завершён; после разрешения владельца рекомендации реализованы
локально 2026-10-21**. [Реализация и финальные проверки](discount-banners-implementation-20261021.md).
Разделы ниже сохраняют исторические результаты и формулировки аудита20 октября;
«сейчас»/«предложение» в них относятся к той точке, а не к новой реализации.
Проверяется наш frontend, его текущие запросы и переходы. Upstream Bot принимается
рабочей основой. Серверные правила скидок и обработка платежей не переоцениваются.

## 1. Главный вывод

`PromoOffersSection.handleUseNow` всегда вызывает `/subscription/purchase`.
Компонент находится на Dashboard, но не получает выбранный `subscriptionId`,
список подписок или результат проверки доступного действия. Поэтому действие
одинаково называется и направляется для разных состояний аккаунта.

Это расходится с уже принятым контекстным управлением: платная обычная подписка
продлевается своим `/subscriptions/:id/renew`, а покупка новой — отдельный сценарий.
Корректный переход не должен сам списывать деньги или создавать покупку.

## 2. Карта модулей и данных

- `Dashboard.tsx` знает `selectedSubscriptionId`, успешно загруженные owned записи
  и полную выбранную подписку; монтирует `<PromoOffersSection />` без этого контекста.
- `PromoOffersSection.tsx` читает `/cabinet/promo/offers` и
  `/cabinet/promo/active-discount`, claim выполняет `/cabinet/promo/claim`.
- «Активировать» и «Использовать сейчас» — разные действия: первое включает
  предложение и перечитывает состояние, второе сейчас лишь меняет route.
- `SubscriptionPurchase.tsx` защищает paid classic: вместо нового оформления
  перенаправляет в управление. В tariff mode открывается каталог/оформление.
- `PurchaseCTAButton.tsx`, `legacySubscription.ts` и subscription navigation
  уже содержат применимые frontend ограничения обычного продления/миграции.
- `usePromoDiscount`/`promoDiscount.ts` используются в classic/tariff purchase;
  renewal показывает суммы из существующего `/renewal-options` напрямую.
- `GiftSubscription` использует свой config, дополнения — свои price quotes,
  публичный `/buy/:slug` — landing config. Процент одного account banner не
  заменяет эти источники истины.

## 3. Что фактически делает «Использовать сейчас»

Browser fixtures,320/1280, без настоящих платежей. IDs42/43 — демонстрационные.

| Состояние | Фактический результат сейчас |
| --- | --- |
| Подписки нет | `/subscription/purchase`, «Оформить подписку» |
| Пробная | Тот же экран оформления |
| Платная classic, активная | Purchase entry → защитный redirect → `/subscriptions/42` |
| Платная classic, истёкшая | Такой же redirect в управление42 |
| Платный обычный тариф | Остаётся `/subscription/purchase`, витрина/оформление |
| Несколько tariff subscriptions, на Dashboard выбрана43, все тарифы куплены | `/subscription/purchase`, «Новый тариф» / «Все тарифы уже куплены» |

Таким образом, для classic есть лишний переход через неподходящий entry, для
tariff нет прямого входа в продление, а выбранная подписка при нескольких
вообще не передаётся. Даже если каталог доступен для новой дополнительной
подписки, это не доказывает намерение пользователя купить именно новую.

## 4. Рекомендуемая матрица назначения

Это **предложение**. Следующий этап — согласование владельцем и отдельная
frontend-реализация одного общего resolver, а не набор разных условий в баннерах.

| Подтверждённое состояние | Предлагаемый переход | Понятное действие |
| --- | --- | --- |
| Подписок нет | Существующий выбор первой платной подписки | «Выбрать тариф» |
| Trial active/expired | Применимый существующий переход на платную подписку | «Выбрать тариф» |
| Одна обычная платная periodic subscription, active/expired, поддерживает нынешнее продление | `/subscriptions/:id/renew` | «Выбрать срок» / «К продлению» |
| Несколько, явно выбрана owned подписка и для неё доступно продление | Продление именно выбранного ID | «К продлению» |
| Несколько, выбранный ID не определён | `/subscriptions`, затем конкретная подписка | «Выбрать подписку» |
| `requires_tariff_selection` | Нынешняя миграция в выбор тарифа с ID | «Выбрать тариф» |
| Daily, limited, disabled или иной случай, где обычное продление не подтверждено | Управление конкретным ID и его существующие доступные действия | «Управление подпиской» |
| Список/подписка ещё загружается либо запрос завершился ошибкой | Pending/retry, не объявлять аккаунт пустым | Состояние загрузки/повтор |

Проверку обычного продления нужно переиспользовать из текущего frontend flow,
включая исключения trial/daily/limited/legacy; не создавать обход этих guards.
У trial при других платных записях сохраняются действующие ограничения classic
entry: generic purchase нельзя использовать для обхода account-wide paid guard.
Условие наличия денег не должно отправлять пользователя сразу пополнять баланс:
сначала показываются срок и подтверждённая цена, затем штатный funding return.

После перехода цена и применимая скидка подтверждаются текущим API выбранного
сценария. Наличие account banner само по себе не доказывает тот же процент на
renewal, устройствах, трафике, подарке или другом действии. Для renewal нельзя
дополнительно вычитать account процент из уже возвращённой серверной суммы.
Ограничение: нынешний ActiveDiscount ответ не содержит универсальной scope-матрицы;
frontend использует существующие доступные действия и quote, не выдумывает её.
Это не предложение менять backend и не новый backend acceptance todo.

## 5. Инвентаризация всех скидочных поверхностей

| Поверхность | Где и когда | Действие сейчас | Рекомендация |
| --- | --- | --- | --- |
| Активная account discount, зелёная Card | Dashboard / PromoOffersSection: `is_active` и percent>0 | «Использовать сейчас» → generic purchase; отдельное отключение | Матрица выше, выбранный ID, свежесть/срок перед переходом |
| Доступное процентное предложение, жёлтая Card | `is_active && !is_claimed` в offers | Claim, success/error, refresh; автоматического перехода нет | Сохранить отдельную активацию, затем контекстное действие активной скидки |
| `test_access` offer | Та же секция, отдельные title/description | Claim, refresh subscription; автоматического оформления нет | Это доступ к серверам, не процентная скидка: после подтверждения показывать применимое управление/подключение, не generic purchase |
| Успех промокода | Balance, после activation | Inline success; выбор подписки при `select_subscription` | Сначала перечитать существующие состояния, не угадывать эффект по bonus_description; ссылку применения показывать только по подтверждённому эффекту |
| «Ваша группа» | Purchase/renewal через PurchaseContextBanners, также Gift | `/info`, раздел loyalty/«Статусы», сохранённый returnTo | Назначение верное: информационная ссылка, не ещё одна активация. Само имя группы не доказывает скидку |
| Бейджи процентов/старая цена/«Выгодно» в периодах и тарифах | PeriodCardContent/TariffPickerGrid/RenewalOptions | Выбор периода/тарифа в текущем сценарии | Оставить локальный выбор; «Выгодно» не является отдельным coupon action |
| Discount indicator дополнений | DeviceTopupSheet/TrafficTopupSheet/SwitchTariffSheet; ServerManagementSheet при включённой опции | Процент/цена текущего quote, свои действия | Оставить в соответствующей докупке/смене; account discount не направлять сюда без подтверждённой применимости |
| Gift active discount | Gift config `active_discount_percent>0` | Информационная строка «Скидка применена», отдельной навигации нет | Сохранить контекст подарка и его API config/quote; группа ведёт в loyalty с возвратом |
| Public landing discount countdown | QuickPurchase `/buy/:slug`, config.discount | Информационный таймер; по окончании скрывается и перечитывается config | Оставить тот же landing; не отправлять в общий кабинет, сохраняя slug/contact/offer context |
| Колесо/результат с промокодом | Wheel result; текущие handlers получают код через Bot | Информация/код, отдельного Use now route нет | Не трактовать любое вознаграждение как скидку; применять подтверждённый код штатным способом |

DashboardPromoCarousel не содержит active-discount slide: там привязка аккаунта,
подключение, первая покупка, канал, подарок и реферальный раздел. Это маркетинговые
ссылки, не тот «Использовать сейчас». WebSocket/SuccessNotificationModal не имеют
отдельного discount Use now handler. Admin offer/template страницы настраивают
предложения, не пользовательскую навигацию применения скидки.

## 6. Дополнительные подтверждённые frontend несоответствия

### 6.1. Промокод и кеш баннера

В Balance после успеха обновляются balance/user, transactions, purchase-options
и subscriptions-list. Не инвалидируются active-discount/promo-offers/group context
и текущие renewal price queries. Особенно заметен `active-discount` с30s cache:
если на Dashboard уже был сохранён ответ «скидки нет», после промокода и быстрого
возврата старое значение может оставаться и зелёный banner не появляется.

Это отдельно воспроизведено на320/1280: mock activation успешна, последующие GET
могли бы дать active=true, но active-discount не перечитан и banner остаётся скрыт.
Применение кода в серверном домене этим тестом не проверялось.

Рекомендация: после успешной активации/отключения синхронизировать существующие
readonly caches скидки, группы, подписок и quote затронутого flow. Не парсить
bonus_description для определения эффекта: текущий activate response не содержит
универсального machine-effect; нужные факты читаются существующими GET.

### 6.2. Истечение срока

PromoOffersSection форматирует past deadline словом «Истекло», но видимость
active/available Card основана на server flags, без отдельного client deadline
check; своего interval у секции нет. `usePromoDiscount` также читает cached
is_active, а не вычисляет срок. Stale active=true payload с past expires_at
сохраняет Use now — browser audit подтвердил это на320/1280.

Это моделирование устаревшего кеша, не утверждение, что Upstream Bot возвращает
неправильные данные. Рекомендация: по времени/перед действием обновить существующий
GET, завершить/скрыть истёкшее предложение и не обещать процент до свежего quote.
Автоматически вызывать отключение/clear endpoint ради таймера не нужно.

### 6.3. Безусловное обещание персональной скидки

«Ваша группа» всегда подписано «Персональные скидки применены к ценам», даже если
наши mock group rates0 и period_discounts пусты. Имени недостаточно для такого
утверждения. Рекомендую нейтральное «Условия вашей группы»; факт применения скидки
оставить там, где он подтверждается данными цены. Для неизвестного offer effect
без процента описание тоже должно оставаться нейтральным, а не обещать скидку.

## 7. Правила дальнейшей frontend-реализации

1. Один resolver действия для активной account discount; Dashboard передаёт уже
   известный выбранный/owned context. Не создавать новый одинаковый list query
   в каждом баннере, не терять ID и не выбирать чужую/другую запись молча.
2. Активация, переход к использованию, подтверждение покупки и отключение —
   разные явные действия. Claim уже не выполняет покупку; это сохраняется.
3. Promocode-source отключается нынешним dedicated endpoint, offer/admin-source —
   существующим clear endpoint. Не объединять их навигационным рефакторингом.
4. Любой итог, скидка и доступность дополнения берутся из действующего API этого
   flow. Нет параллельного pricing engine или требований к новым backend полям.
5. Нужны tests на readonly API mocks:0/trial/paid/expired/multiple/legacy/daily/
   limited/ошибка, сохранение ID, expiry, invalidation, отсутствие purchase POST
   от активации или одного перехода. Никаких реальных финансовых действий для аудита.

## 8. Доказательства и статус решения

Код скидочных handlers в этой задаче не менялся. Реализованы только отдельно
запрошенные UI изменения Subscription: убрать верхний WebBackButton и перенести
balance-autopay toggle под Additional options. Их проверки — отдельный UI record.

Локальные receipts `.scratch/promo-banners-20261020/`:

- `browser-audit-verified.json/.log`: **18 PASS**,320/1280 —6 текущих Use now
  destinations, stale expiry payload и2 claim effect сценария. Это доказательства
  **нынешнего** поведения, не acceptance предложенных исправленных маршрутов.
- `browser-promocode-cache.json/.log`: **2 PASS**, воспроизведение stale cache.
- `audit.spec.ts`: все API замоканы, actual purchase/renew POST не выполняются.
- Первый audit12/18 с6 fixture failures сохранён: hidden native option вместо
  значения select и неправильный guessed claim URL. Harness исправлен под
  фактический `/cabinet/promo/claim` и selected value; runtime не менялся.

Проверка query/price/offer scopes — по frontend consumers и существующему API
контракту. Live/backend/financial/Release PASS не заявлены. Матрица назначения,
обновление кеша и expiry UI на момент аудита оставались **предложением на
подтверждение владельца**. После разрешения продолжить они реализованы21 октября:
1161 unit PASS,821 compiled browser PASS/5 configured SKIP/0 FAIL,32 banner captures,
build/оба TypeScript/Biome PASS. Исторические audit assertions не являются acceptance
новой версии; отдельный итог и identities — в ссылке в начале документа.

Рекомендуемый уровень рассуждения для следующей задачи: высокий — реализация должна согласовать тип выгоды, выбранную подписку, актуальность скидки и существующие финансовые переходы.
